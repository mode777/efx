# Design

Implements F4a (Phong lighting, no maps). Motivation and scope:
`proposal.md`; behavior contract: `specs/lighting/`, `specs/3d-core/`,
`specs/js-api/`. Decisions here are numbered D1–D12 and referenced by
`tasks.md`.

## Context

`src/` is a core static lib (`platform`, `runtime`, `api`, `player`,
`render`) plus `main.c` (ADR 0003). F3 shipped the mesh path: interleaved
`pos(3f) normal(3f) uv(2f) color(4f)` vertex layout per surface (absent
attributes default to normal `(0,0,1)`, uv 0, color white), one GPU draw per
surface, a depth-tested mesh record holding `{mesh, transform[16], color[4],
camera}` value-snapshotted at record time (ADR 0019), and a single unlit mesh
shader generated by sokol-shdc (ADR 0021) from `shaders/mesh.glsl`. GPU work
goes through the `efx_render_sink` vtable; sokol only lives in
`src/platform/pipeline.c`; GLM sits behind the plain-C wall in `src/math`
(ADR 0005). There is currently **no** light or material storage anywhere in
`src/` (F3 only reserved the concept in the spec). Fixed limits: 4 point
lights + 1 directional light (vision.md). F2 2D behavior and its seven goldens
are frozen.

## Goals / Non-Goals

**Goals:**

- A lit mesh path: world-space Phong over interpolated normals, driven by
  four point lights and one directional light plus a per-surface material.
- Per-surface material bindings made real (creation-time `materials` array +
  `setMeshSurfaceMaterial`), with no global material state.
- A CPU reference implementation of the exact F4a equation, unit-tested.
- F2 2D records and goldens byte-identical; F4a lighting goldens added and the
  six F3 mesh goldens re-baselined as an intended output change.
- Identical semantics across the quickjs desktop binding and the web bridge.

**Non-Goals:**

- Maps, texture sampling on meshes, and alpha masks (F4b) — `uvs` stay
  unused by lighting here.
- Per-material shader permutations (deferred; F4b introduces the first one).
- Shadows, spot lights, multiple cameras, HDR/tonemapping/gamma, per-draw
  material overrides, any consumer-visible shader surface (ADR 0015).

## Decisions

- **D1 — Lighting is evaluated in world space, per fragment, Blinn-Phong.**
  The vertex shader transforms the object position by the model matrix to
  world space and the normal by the normal matrix; the fragment shader
  normalizes the interpolated normal and computes ambient + diffuse +
  specular + emissive against light positions/directions and the camera
  position. Alternative (object space) needs an inverse model matrix to bring
  lights into object space and breaks under scaling; alternative (view space)
  forces every light into view space at playback and couples lighting to the
  camera. World space is the least surprising for a fixed-function model and
  the easiest to mirror on the CPU (D8).
- **D2 — One lit mesh shader, uniform-driven; no F4a permutations (ADR 0026).**
  `shaders/mesh.glsl` is extended from the F3 unlit fill into the Phong shader
  and regenerated with the pinned sokol-shdc (ADR 0021). Lights and material
  channels are uniforms, so the shader does not branch on which channels are
  present. Alternative (build-time permutations keyed by material feature set)
  is exactly what F4b's maps will need; introducing the machinery before there
  is a feature to permute adds pipeline/selection complexity for nothing.
  Alternative (keep the unlit shader alongside a separate lit shader and
  select per surface) loses: it contradicts the settled "default material =
  white diffuse Phong" contract and doubles the pipeline surface with no F4a
  need. This decision is recorded durably as ADR 0026 because F4b/F5 must
  respect it.
- **D3 — Matrix plumbing: `mvp` (as F3) plus `model` and a CPU-computed
  normal matrix.** Playback composes `model` from the record, `vp` from the
  recorded camera (D3 of F3, re-evaluated for the active pass aspect), then
  passes `mvp = vp × model`, `model`, and `normal = transpose(inverse(mat3(model)))`.
  Alternative (transform normals by the model 3×3) is wrong under non-uniform
  scale, which `drawMesh` permits; computing the normal matrix once per record
  on the CPU is cheap and keeps the shader exact.
- **D4 — The light bank is value state; each mesh record snapshots it.**
  The engine holds four point slots + one directional slot; `drawMesh`
  snapshots the whole set into the record (ADR 0019), so playback is
  independent of later `setLight` calls and the display list stays
  re-orderable. Alternative (a single global light buffer read at playback)
  violates the value-snapshot contract and makes records non-self-contained.
  The snapshot is small (four `pos`/`color` pairs + direction/color), well
  within the byte-based record budget.
- **D5 — Material bindings are per-surface snapshots; materials are
  JS-managed (resource exposure).** `setMeshSurfaceMaterial` validates a
  script object and stores a plain value snapshot (four channel colors +
  shininess + bound flag) in the Mesh's per-surface binding; `createMeshData`
  stores the `materials` array into the MeshData and it carries over at
  upload. Materials therefore have **no native handle and no `destroy()`** —
  the ADR 0011/0012 memory rules do not apply to them because nothing
  unmanaged is held. The only fixed bank is lights, exposed as the four
  pre-allocated slots of D4 (ADR 0011 slot model). No new native-backed class
  is introduced, so the `js-api` native-class list is unchanged.
- **D6 — Default material and missing attributes.** An unbound (or
  `null`-bound) surface uses the engine default material: white diffuse
  Phong — ambient/emissive/specular black, `shininess` 32, diffuse white.
  A surface with no `normals` keeps F3's deterministic `(0,0,1)` normal, so
  lighting is defined for every F3-legal mesh. Surface alpha is the albedo
  alpha (vertex-color alpha × tint alpha); material channel alphas are
  ignored in F4a. `uvs` remain validated and stored but unread.
- **D7 — Exact F4a equation (pinned for the CPU reference and goldens).**
  With `albedo = vertexColor × tint`, `N` the unit world normal, `V` the unit
  camera direction, and per enabled light `L` the unit direction to the
  light: `final = ambient.color×albedo + diffuse.color×albedo×Σ(light.rgb×max(N·L,0)×atten)
  + specular.color×Σ(light.rgb×max(N·H,0)^shininess×atten) + emissive.color`,
  with `H = normalize(L+V)`, `atten = range==0 ? 1 : clamp(1 - d/range, 0, 1)`
  for point lights and `atten = 1`, `L = normalize(-dir)` for the directional
  light. Output is clamped to `[0,1]` per channel; no HDR. Emissive is added
  unmodulated by the albedo. The spec text in `specs/lighting/` is the single
  source for both the shader and the CPU reference.
- **D8 — CPU lighting reference is a pure-C core module.** A small module in
  `src/render/` (no sokol, no quickjs — module walls) implements D7 over
  plain values, plus a headless unit test with analytic cases. The shader and
  the reference are transcribed from the same spec text; golden scenes are the
  arbiter that the GPU agrees (roadmap: F4 verified against a CPU reference).
- **D9 — Golden strategy.** Add F4a scenes (ambient/diffuse, directional,
  specular, attenuation, emissive, multi-material/default-material) and
  re-baseline the six F3 mesh scenes, whose setup gains explicit lights and
  materials so the images stay meaningful. The seven F2 2D goldens MUST remain
  byte-identical (task-level check). New and re-baselined scenes require the
  manual server-side llvmpipe capture before remote verification
  (`docs/verification-server.md`).
- **D10 — Validation split mirrors F3.** Type-level errors (wrong JS types,
  unknown fields, both/neither mesh form) are raised in the bindings
  (`src/api/api.c`, `src/web/bridge.c`); range-level errors (slot index,
  surface index, `materials` length, `shininess`, `range`) are enforced in the
  shared render core where possible so desktop and web cannot drift.
- **D11 — No depth/attachment change.** F4a touches fragment shading only; the
  ADR 0025 clip-depth remap and pipeline attachment setup are unchanged.
- **D12 — Record durability.** The mesh record grows by the light snapshot
  (D4) and the material bindings live on the Mesh (D5), not in the record, so
  records stay self-contained and small. No new record type is needed.

## Risks / Trade-offs

- [Cross-backend specular/precision drift breaks goldens] → keep the equation
  to `dot`/`max`/`pow` with no transcendentals beyond `pow`; rely on the
  ±2/255 golden tolerance; lighting goldens use smooth surfaces (sphere) and
  moderate shininess.
- [Re-baselining F3 goldens masks an F3 regression] → keep the seven F2
  goldens byte-identical and add explicit F4a scenes; the F3 scene *geometry*
  assertions (multi-surface, depth, transform) remain, only shading changes;
  the re-baseline is an intended output change per the verification spec.
- [Normal skew under non-uniform scale] → CPU normal matrix (D3).
- [Record/budget growth from the light snapshot] → budget is byte-based with
  ample headroom at PS2-era scene counts; a mesh record is still one record.
- [sokol-shdc uniform-array/block limits differ per backend] → verify the
  generated header compiles on the GL/D3D11/Metal/Emscripten paths before
  wiring playback; keep each uniform block well under the 4 KB limit.
- [Desktop/web drift in material/light validation] → share the range-level
  validation in the core (D10) and run `tools/run_web_compare.mjs` over the
  F4a smoke scripts.

## Migration Plan

No data migration: no shipped scripts depend on F4a (the API was provisional
in `docs/js-api.md`). `docs/js-api.md` moves the F4a entries from provisional
to current in the same change. Rollback is a revert of the change branch;
goldens are additive plus re-baselined in place. F2 behavior and goldens are
untouched throughout.

## Open Questions

None. The F4b permutation/maps strategy is explicitly future scope (D2) and
does not change this design; per-surface material snapshots (D5) are the
additive seam F4b extends.
